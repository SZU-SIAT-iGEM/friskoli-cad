# 系统级数值执行与资源规则

2026-10-03：新统一 profile 的全图 planner、模块执行合同、端口/状态资源预算及事务时序见[系统运行图](system-execution.md)。CPU-only 模块继续在 CPU，已声明 CUDA 的系统扩散使用显式 host/device 传输；不是整图 GPU 驻留。旧 profile 的数值算法与下方已有验证保留。

这些机制适用于空间执行规则中的所有已注册模块。案例只保存对象、参数和图连接，不依据案例 ID 选择求解逻辑。科学行为通过模块声明；调度、有限库存结算、存储和资源校验由系统处理。

## 大网格与后端

空间网格上限为 256³。实际任务还需通过内存、输出、磁盘和设备资源预检；上限不是机器可用资源的保证。超过 10000 个体素的场保存为连续 float64 数组，不为每个体素建立 Python float 对象。数组由不可变 bytes 持有，图输出、状态和回放快照可以安全共享；候选步单独持有可写数组，失败不提交。

`numpy-cpu` 与 `numpy-cupy-cuda` 都使用相同的六邻接有限体积通量及无通量边界。CUDA 仅处理扩散数组，科学模块、碰撞与独立 RNG 继续按同一调度执行。后端必须显式选择；CUDA 不可用时不会静默改用 CPU。设备能力需要真实编译并执行 float64 kernel 后才公布。CUDA 不启用 fast math 或 FMA，保留有限非负与守恒检查。

可选安装依赖为 `friskoli-cad[cuda11]`，还需兼容的 NVIDIA 驱动和 CUDA 11 NVRTC 运行库。Windows 上可复用已安装 PyTorch 中的 CUDA 运行库，无需导入 PyTorch；其他机器按 CuPy 的运行库要求安装。任务来源记录 CuPy、CUDA runtime、驱动和设备；GPU checkpoint 也锁定这些信息。CPU 使用方式与旧合同保持兼容。

## 有限库存的可表示转移

菌体请求使用步初场值，扩散后再从局部库存扣减。扩散前沿可能使请求远小于更新后的库存，一个理想扣减即使非零，也未必能由 float64 余浓度精确表示。

系统先按可用库存计算共同请求的比例分配。如果原计算已满足现有转移精度预算，保留原结果；否则在提交前选择不大于理想量的可表示扣减，并按相同比例分配给菌体。未满足量保留在原来的场内。实际接受量驱动摄取、信号与生理模块，不能先给菌体记账再忽略场的扣减。

`FieldLedger.representability_shortfall_molecules` 保存每步由于表示能力产生的未满足量，并进入 checkpoint。这是数值诊断，不是生物摄取阈值、附加养分池或饥饿模型。如果请求小于可表示扣减，该步实际接受量可以为零；因此不能声称任意小 dt 下的所有微量通量都得到精确解析。转移与总账的既有守恒容差没有放宽，也不通过失败后缩步或重复提交解决。

胶囊生长同样以实际可表示的几何增量结算养分；尚不足以改变几何的养分留在胞内库存。方程给出的理想增量与最终几何更新需要区分，不能消耗养分后报告没有实际写入的生物量。

## 显示与原始数据

Task 0.5 可以显式设置 `field_stride_xyz`，每个轴必须整除计算网格。回放场使用体积平均，并同时标注计算与显示格距；计算网格不变。`include_final_fields` 独立导出完整最终场 NPZ，包含数组、单位、计算域、摘要与 SHA-256。NPZ 不含 pickle，下载后可用 `numpy.load(..., allow_pickle=False)` 读取。具体合同见 [场预览与原始导出](task-field-previews.md)。

10000 步的完整场景验收记录在 [N5 验收](verification-n5-simulation.md)。当前大场性能分析和加速是N5前置任务，见[剩余清单 P01–P04](remaining-work.md)。开发须剖析真实负载，在相同科学参数、网格、dt及精度下比较实现并验证结果；最终使用体验由用户验收。不以扩大时间步、缩小场景或降低精度作为系统优化的证据。
