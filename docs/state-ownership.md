# 状态归属与后续扩展

给系统增加底层信息会影响保存格式、计算模块和前端。现有模块接口能减少牵连，但不能保证“后来加字段完全无影响”。每增加一种状态，先确定它属于谁、单位是什么、由谁更新、哪些模块读取，以及怎样写入可回放结果。

| 信息 | 归属与更新方式 | 当前实现 |
| --- | --- | --- |
| 某种物质的浓度 | 环境中按物种标识的空间场；输入、摄取、释放和输运分别改变它 | `species` 参数约束模块连接；运行快照按物种保存浓度场。示例用 `substrate`，项目级物种目录尚未建立 |
| 环境黏度 | 介质属性。若空间均匀，可先是环境模块参数；若随位置或时间变化，需要环境状态场与更新模块 | 协议可声明带 `quantity`、单位的 `field.scalar` 端口；尚无黏度模块、场或经验证的关系式 |
| 扩散系数 | 具体物种在指定介质和条件下的输运参数，或由环境属性计算出的场 | 扩散的数值执行尚未接入；不能仅因有浓度场就推定扩散已发生 |
| 菌体尺寸 | 单菌体几何状态。菌体组可给初始模板，实际运行需能保存每个菌体的尺寸 | 当前只有 ID、中心与朝向；尺寸、增长和分裂时的几何更新尚未实现 |

这里说的黏度首先指**环境介质的动态黏度**，单位可声明为 `Pa*s`。若研究的是菌体内部黏度，它应归于对应菌体状态。黏度与扩散系数有联系，但不能把它们合成一个字段：某种分泌物增加时，可以先改变该物质的浓度，再由经过定义的介质模块计算黏度场，输运或运动模块读取这个场。浓度可换算并核对物质分子数；黏度没有同样的物质守恒账。没有关系式时，系统不应自行推算。

## 菌体尺寸的后续接入

用户提出的顺序是：先声明初始尺寸，再由生长模块改变单菌体尺寸；分裂后，延续原 ID 的菌体与获得新 ID 的菌体各有明确的几何和其他状态。几何应在运行时有唯一来源，前端读取结果帧显示，不能在前端独立“长大”。分裂还需规定所选状态如何分配，以及该状态是否应守恒；不同状态不能套用同一条分割规则。

现有 `CellGroup` 没有尺寸字段，`0.1.0` 单菌体帧也拒绝未声明字段。因此接入时要修订版本化协议、运行时状态与旧项目读取方式；需要尺寸的模块在输入缺失时明确报错，旧模块继续按其声明的接口运行。物理形状的具体表示法和生长方程待有科学依据时确定。当前空间采样模块的 `support_*_um` 是作用范围，不能当作初始尺寸。

## 对现有接口的判断

目前模块端口按**形状、物理量、单位、物种**检查连接；模块声明带版本，行为图带协议版本。运行器已处理 `field.scalar` 与 `cell.scalar`，环境快照可携带多个带类型的场。这为增加功能提供了明确边界。后续每次扩展仍需保存格式迁移、旧图兼容检查和新功能的数值验证。项目级物种目录、通用环境属性目录、动态尺寸与运行中模块状态迁移都尚未完成。
